# Guest→Host Syscall Payload Contract v1

## Scope

This document specifies the project-owned binary wire format used for MuduDB
guest→host syscalls.

The wire format keeps the 16-byte header introduced in Phase 1 and encodes the
message body with **MessagePack**. The MessagePack layout is **project-controlled**:
it is derived from the canonical WIT definitions in
[`mudu_binding/wit/`](../../../mudu_binding/wit/) and generated by `mgen` into
custom `serde` implementations for Rust and custom MessagePack formatters for C#.
The implementation uses `rmp_serde` (or an equivalent MessagePack runtime on the
C#/AssemblyScript/Python side) only as the low-level encoder/decoder; it does **not**
use the default `rmp_serde` derive behavior, which would serialize Rust enum
variants as maps or strings and would not be stable across guest languages.

The canonical syscall boundary is the WIT function interface declared in
[`uni-syscall.wit`](../../../mudu_binding/wit/uni-syscall.wit). The header and
MessagePack body described here are the runtime's internal serialization of
those WIT function calls; guest code should call the WIT functions directly and
let the generated bindings handle the wire format.

The logical data model is the existing `mudu_binding::universal` type family;
this contract defines the **wire encoding** of those types.

**Status: implemented and stable.** All 23 message kinds are encoded and
decoded by the host router in
[`mudu_binding/src/codec/syscall_payload/`](../../../crates/common/mudu_binding/src/codec/syscall_payload/)
and dispatched in `mudu_runtime` (`kernel_sync` / `kernel_async`). Guest-side
implementations exist for workspace Rust guests, the standalone Rust SDK, the
C# SDK, AssemblyScript (direct byte-pipe guest with an in-language codec), and
Python (a
tooling/corpus-verification binding); see
[Guest language support](#guest-language-support) below and the
[Guest/Host ABI integration guide](../abi/guest_host_abi.md). Byte-level
interoperability of the independent codecs is verified against a single
host-generated golden corpus (see
[Interop verification](#interop-verification)).

The obsolete `UniDatTypeId` / `UniMuTypeFamily` enumerations are not part of
this contract and have been removed from the binding layer. When a type-family
value needs to cross the boundary, it is carried inside `UniDataType` /
`UniScalar` instead.

## Registry

| Property | Value |
|----------|-------|
| Format family | `FormatKind::SyscallPayload` |
| Magic | `0x4D53_5350` (ASCII `MSSP`) |
| Current version | `1` |
| Supported range | `[1, 1]` |
| Registry | [`mudu/src/compat/mod.rs`](../../../mudu/src/compat/mod.rs) |

The runtime decodes only the current version. An unsupported version fails fast
with `ErrorCode::UnsupportedFormatVersion`. When the format version changes, MPK
packages are rebuilt for the matching runtime; the runtime does **not** retain
legacy decoders.

The same version is pinned into every MPK package: `package.manifest.json`
carries a `syscall_abi_version: u32` field. The package writer (`mpm_build`)
always emits `SYSCALL_PAYLOAD_CURRENT_VERSION` (`1`); the loader in
[`mudu_runtime/src/service/app_package.rs`](../../../crates/db-kernel/mudu_runtime/src/service/app_package.rs)
defaults a missing field to `1` and rejects any mismatch with
`ErrorCode::UnsupportedFormatVersion` ("unsupported syscall ABI version
{found}, expected {expected}"). `FormatKind::SyscallPayload` is registered in
the global `CompatibilityRouter`
([`mudu_kernel/src/compat.rs`](../../../crates/db-kernel/mudu_kernel/src/compat.rs))
with an identity v1 migration handler in
[`mudu_binding/src/codec/syscall_payload/migrate/`](../../../crates/common/mudu_binding/src/codec/syscall_payload/migrate/);
migrate units are complete frames (16-byte header included).

## Field-number evolution policy

The map keys of record fields and request parameters are the 1-based integers
of WIT declaration order (protobuf-style). Once a schema ships, evolution is
**append-only**:

- **New fields/parameters** are appended at the end of the WIT declaration
  and take the next field/parameter number. Old decoders skip unknown keys
  under the lenient-decode rules; new decoders default missing fields — old
  and new codecs interoperate within the same version.
- **Field numbers are never reused**; reordering or renumbering existing
  fields is forbidden (declaration order **is** the wire numbering).
- **Deleting a field** keeps its number reserved: remove the field from the
  declaration and mark the slot `reserved` in a comment (both the number and
  the name stay reserved) so it cannot be accidentally reused.
- **New syscalls** are appended at the end of `uni-syscall.wit` and take the
  next `message_kind`; **new variant cases** are appended and take the next
  tag.

All of the above is **in-version schema evolution** and does not bump
`version` — lenient decoding keeps old and new peers interoperable within the
same version. `version` increments only when the encoding rules themselves
change (see [Header](#header) below and
[Upgrade and rollback rules](#upgrade-and-rollback-rules)).

## Payload layout

Every syscall request and every syscall response is encoded as a single
self-describing message:

```text
+--------------------------------+
| Header (16 bytes)              |
+--------------------------------+
| Body (variable, MessagePack)   |
+--------------------------------+
```

There is no separate length prefix outside the header; the WIT transport
delivers the exact byte range.

### Header

All header fields are **big-endian**.

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0 | 4 | `magic` | Magic `0x4D53_5350` (ASCII `MSSP`). |
| 4 | 4 | `version` | Payload format version. Current value: `1`. |
| 8 | 4 | `flags` | Reserved. Must be `0`; decoders reject any non-zero value. |
| 12 | 4 | `message_kind` | Message-kind discriminant. Still present in the wire header for routing, but the set of valid kinds is defined by [`uni-syscall.wit`](../../../mudu_binding/wit/uni-syscall.wit), not by this document. |

`version` is the **payload format version**, not the WIT interface version. It
increments only when the **encoding rules themselves** change — for example
integer semantics, the header layout, or the map/array structural rules.
Schema evolution (appended fields, appended `message_kind`s, appended variant
tags) is absorbed in-version by the field-number mechanism and does not bump
`version` (see [Field-number evolution policy](#field-number-evolution-policy)).

The WIT function interface in `uni-syscall.wit` is the authoritative definition
of which syscalls exist and what their request/response types are. The runtime
maps each WIT function to the same internal header + MessagePack path; the
`message_kind` discriminant is therefore an implementation detail retained for
runtime routing.

The fs records are WIT records with the following wire shapes (a record is a
MessagePack map keyed by the 1-based field numbers in declaration order):

- **`UniFsOpenArgv`** — `{1: session: UniOid, 2: oid: UniOid, 3: path: string, 4: flags: u32}`.
- **`UniFsStat`** — `{1: oid: UniOid, 2: generation: u64, 3: entry: string, 4: length: u64, 5: state: u32}`.
- **`UniFsDirent`** — `{1: name: string, 2: is_dir: bool, 3: length: u64}`.

For the relation syscalls, `key` is a list of `(column_index, column_value)`
pairs identifying the primary key, `select` is the list of column indices to
project, `values` is a list of `(column_index, column_value)` pairs to write,
and `deltas` is a list of `(column_index, op, operand)` triples for in-place
numeric updates. Tuples encode as fixed-length MessagePack arrays.

**Exception: `fetch`.** The host WIT function
`fetch(query-result: list<u8>) -> list<u8>` declared in the runtime world
([`mudu_runtime/wit/api.wit`](../../../crates/db-kernel/mudu_runtime/wit/api.wit))
is **not** routed through MSSP: it takes and returns raw `mp_wire` bytes
with no 16-byte header. The request is the `mp_wire` encoding of a
`UniOid` (a field-number map) — exactly the bytes carried in
`UniResultSet.cursor` of a query
response. The response is the `mp_wire` encoding of
`UniResult<UniResultSet, UniError>` (a one-entry map envelope
`{0: value}` / `{1: error}`). The host implementation
(`mudu_runtime::interface::kernel_sync::fetch_internal`) mirrors
`sys_interface::api_impl`
([`crates/common/sys_interface/src/api_impl/mod.rs`](../../../crates/common/sys_interface/src/api_impl/mod.rs)),
which remains the wire-shape source of truth. Semantics:

- `fetch` drains **all** cached rows of the cursor's result set and always
  reports `eof: true`.
- A `fetch` after the result set is drained returns an empty `row_set` with
  `eof: true` — this is **not** an error.
- An unknown cursor yields `UniResult::Err` with
  `ErrorCode::EntityNotFound`; a malformed cursor yields `UniResult::Err`
  (every failure is encoded into the `UniResult` envelope because the WIT ABI
  returns a bare `list<u8>` with no error channel).
- Queries on synchronous connections cache their result set on the session
  `Context` so a later `fetch` can drain it; queries on asynchronous
  connections are never cached, so a `fetch` after an async query returns an
  empty `row_set` with `eof: true`.
- Cache lifecycle: the cache is drained destructively, `Context::query_next`
  clears it once the result set hits EOF, and `Context::remove` on session
  close drops any undrained cache.

### Pinned wire quirks

The following behaviors are part of the v1 contract and are verified
byte-exact by the golden corpus; independent implementations must match them:

- **Canonical encode, lenient decode:** encoders always emit the canonical
  form (map keys in ascending field-number order, minimal-width integers,
  bin8 threshold); decoders are lenient — integers of any MessagePack width
  are accepted (with a range check on narrowing), unknown map keys are
  skipped, missing fields default (proto3 semantics), and map key order is
  free. Record/request bodies must still be maps, tuple lengths are exact,
  and unknown variant tags are rejected.
- **`UniError.err_details` and `UniResultSet.cursor`** encode as MessagePack
  **arrays** of integers, **not** as MessagePack bin, even though both are
  `Vec<u8>` (`list<u8>`) fields: in the record context `list<u8>` always
  encodes as an array (only func-level blobs encode as bin). Independent
  codecs must accept and emit the array form for these two fields.
- **Integer compaction:** `rmp_serde` emits the shortest MessagePack integer
  form. Small non-negative integers are fixints (e.g. `0` → `0x00`); small
  negative integers are negative fixints (e.g. `i64 -2` → `0xFE`). Do not
  assume a fixed integer width.
- **Blob encoding:** `list<u8>` blobs use bin8 (`0xC4`) when shorter than
  256 bytes, bin16/bin32 beyond that.
- **`err_src` of a source-less host error** is the JSON string `"None"`
  (the host serializes `Option<ErrorSource>` as JSON text).
- **fs errno mapping:** host error code `50029`
  (`ErrorCode::InvalidArgument`) is mapped to guest-facing `EINVAL` (`22`,
  `ErrorCode::InvalidInput`) by `sys_interface::fs::map_fs_errno`.

## Body encoding

The body is a single MessagePack value. The exact byte sequence is controlled by
the `mgen` templates and must not be inferred from generic `rmp_serde` defaults.

### MessagePack encoding rules

The generated code obeys the following rules, which override any default
`rmp_serde` behavior:

| WIT construct | MessagePack encoding |
|---------------|----------------------|
| `record` | MessagePack **map** keyed by the 1-based field numbers (declaration order); values are the encoded fields. Encoding writes all fields in ascending key order. |
| WIT func parameter list | Same as a record: a MessagePack map keyed by the 1-based parameter numbers. |
| `variant` | Two-element MessagePack array `[tag, payload]`. `tag` is a `u32` discriminator assigned by declaration order (starting at `0`). If a case has no payload, `payload` is a dummy `0u8` so the array always has length `2`. |
| `enum` | Bare `u32` discriminant, assigned by declaration order (starting at `0`). |
| `list<T>` | MessagePack array of encoded `T`. |
| `option<T>` | MessagePack nil for `none`; otherwise the encoded `T` for `some`. |
| `result<T, E>` | MessagePack array `[ok_tag, value]` where `ok_tag` is `0u8` for `ok` and `1u8` for `err`, followed by the encoded `T` or `E`. |
| `string` | MessagePack str. |
| `list<u8>` / `blob` | MessagePack bin at the func level; a MessagePack integer array in the record context (this is why `UniError.err_details` and `UniResultSet.cursor` are arrays); see [Pinned wire quirks](#pinned-wire-quirks). |
| Primitive scalars (`u8`, `i32`, `u64`, `f32`, `bool`, `char`, ...) | Standard MessagePack integer/float/bool/str representations. |
| `box<T>` | Same encoding as `T`; the box is transparent on the wire. |

All body values go through **one hand-written generic runtime per language**
(on Rust, `mudu_binding::universal::mp_wire`): it encodes canonically exactly
like `rmp_serde` 1.3.1 (minimal-width integers, str8/bin8 thresholds) and
decodes leniently — integers of any MessagePack width are accepted (with a
range check on narrowing), unknown map keys are skipped, missing fields
decode to the type default (proto3 semantics) and map key order is free.
Structure stays strict: a record/request body must be a map, tuple lengths
are exact and unknown variant tags are rejected. The C#, AssemblyScript, and
Python sides generate equivalent runtime code from the same WIT.

### `OID` / `UniOid`

`OID` is the logical 128-bit object identifier (`mudu::common::id::OID`). On
the wire it is encoded as a `record` with two `u64` fields, the MessagePack
map `{1: h, 2: l}`. Decoders reconstruct the logical
OID as `((h as u128) << 64) | (l as u128)`.

### Composite type layouts

The MessagePack encoding of each record/variant follows the generic rules above.
For reference, the field order and payload shapes are:

- **`UniOid`** — `{1: h: u64, 2: l: u64}`.
- **`UniSqlStmt`** — `{1: sql_string: string}`.
- **`UniSqlParam`** — `{1: params: list<UniDataValue>}`.
- **`UniTupleRow`** — `{1: fields: list<UniDataValue>}`.
- **`UniFieldAttr`** — `{1: attr_name: string, 2: attr_value: string}`.
- **`UniRecordField`** — `{1: field_name: string, 2: field_type: UniDataType, 3: field_attrs: list<UniFieldAttr>}`.
- **`UniRecordType`** — `{1: record_name: string, 2: record_fields: list<UniRecordField>}`.
- **`UniResultType`** — `{1: ok: option<UniDataType>, 2: err: option<UniDataType>}`.
- **`UniResultSet`** — `{1: eof: bool, 2: row_set: list<UniTupleRow>, 3: cursor: list<u8>}`.
- **`UniError`** — `{1: err_code: u32, 2: err_msg: string, 3: err_src: string, 4: err_loc: string, 5: err_details: list<u8>}`.
- **`UniQueryArgv`** — `{1: oid: UniOid, 2: query: UniSqlStmt, 3: param_list: UniSqlParam}`.
- **`UniCommandArgv`** — `{1: oid: UniOid, 2: command: UniSqlStmt, 3: param_list: UniSqlParam}`.
- **`UniQueryResult`** — `{1: tuple_desc: UniRecordType, 2: result_set: UniResultSet}`.
- **`UniCommandResult`** — `{1: affected_rows: u64}`.
- **`UniCommandReturn`** — variant: `ok(UniCommandResult)` or `err(UniError)`.
- **`UniQueryReturn`** — variant: `ok(UniQueryResult)` or `err(UniError)`.
- **`UniSessionOpenArgv`** — currently a hand-written Rust record; its wire shape
  is `{1: worker_id: UniOid}`. It does not yet have a dedicated WIT file; if it is
  moved into WIT in the future it will follow the same encoding rules as above.
- **`UniFsOpenArgv`** / **`UniFsStat`** / **`UniFsDirent`** — see
  [Message kinds](#message-kinds).

## Relationship to the legacy session codec

All 23 kinds — including the KV syscalls (`Open`..`Range`) — are now encoded
and decoded through the framed MessagePack path in
[`mudu_binding/src/codec/syscall_payload/`](../../../crates/common/mudu_binding/src/codec/syscall_payload/),
wrapping each payload in the 16-byte header and using the project-controlled
MessagePack `Result<T, E>` encoding for errors instead of the legacy `MERR`
magic escape. The earlier hand-written binary session codec in
`handle_sys_session.rs` followed conventions matching this contract's
primitives; the Phase 2 unification onto the project-controlled MessagePack
path is complete.

## Integrity mechanisms

- **Magic check:** decoders reject messages whose magic is not `0x4D53_5350`.
- **Version check:** decoders reject any version outside `[1, 1]`, mapping to
  `ErrorCode::UnsupportedFormatVersion`.
- **Flags check:** decoders reject any non-zero `flags` value.
- **Message-kind validation:** decoders reject unknown/`0` `message_kind` values.
- **Length checks:** decoders require at least 16 bytes for the header.
- **MessagePack structural validation:** decoders reject malformed MessagePack
  payloads, trailing bytes after the body, unknown variant tags, and
  record/request bodies that are not maps. Decoding inside a map is lenient
  (unknown keys skipped, missing fields defaulted, any integer width), but
  narrowing overflow and type mismatches are still rejected.
- **UTF-8 validation:** `string` fields must be valid UTF-8.

Structural body decode failures map to `ErrorCode::Decode`. Magic mismatches map
to `ErrorCode::CorruptedData` via the compatibility registry.

## Benchmarks

The host codec is benchmarked by
[`mudu_binding/tests/syscall_payload_bench.rs`](../../../crates/common/mudu_binding/tests/syscall_payload_bench.rs),
following the repo convention of manual-timing `#[test]` benchmarks (no
criterion). Run it with:

```sh
cargo test -p mudu_binding --test syscall_payload_bench -- --nocapture --test-threads=1
```

### Methodology

- **Workloads:** query requests (short SQL with 10 params; ~4 KB SQL with 100
  params); query results with 1, 100 and 10 000 rows of mixed
  int/text/blob/float/bool/null-placeholder columns; KV get/put/delete/range
  requests and ok results (range result with 100 pairs); an fs-open request and
  an fs-readdir result with 50 entries; and a `UniError` error response.
- **Baseline:** every workload is also timed against a *raw* `mp_wire`
  baseline that encodes/decodes the **byte-identical MessagePack body value**
  with no
  16-byte header and no message-kind routing. The
  framing overhead is reported as `(mssp − raw) / raw` per direction; this
  percentage is the machine-independent figure, while absolute µs/op values are
  indicative only.
- **Timing:** 10% warmup iterations, then N timed iterations, wall-clock via
  `mudu_sys::time::instant_now()`. Each workload first asserts
  decode(encode(x)) round-trip correctness and that the raw baseline body is
  byte-identical to the MSSP frame body.
- **No allocation counting:** the repo has no allocation-tracking
  infrastructure and bench conventions forbid new dependencies (no criterion,
  no `stats_alloc`/`dhat`), so only wall-clock time and payload sizes are
  reported.
- **Environment of the recorded run:** AMD Ryzen 9 3900X, dev (unoptimized)
  cargo profile, single test thread, 2026-08-26. Re-run the bench for current
  numbers; treat the table below as an order-of-magnitude reference.

Reading the numbers:

- **Encode framing overhead is small once the body exceeds ~100 bytes**
  (≈0–17%, within noise for multi-KB bodies); the fixed cost is one extra
  frame allocation plus a 16-byte header copy. It only stands out on tiny
  frames (unit results, small error/value bodies) where it reaches ~40–66%.
- **Decode framing overhead is proportionally larger** — roughly +40–50% even
  for multi-KB bodies and up to ~3× on sub-100-byte frames. Besides header
  validation and kind routing, the framed decoder rejects trailing bytes and
  converts values per type, whereas the baseline only decodes the dynamic
  value. The absolute
  penalty is a fixed sub-microsecond-to-microsecond cost per frame, negligible
  next to any real syscall work.
- The design plan (`doc/cn/todo/project-controlled-guest-host-abi.md`, §4)
  originally assumed a big-endian-tagged body encoding and planned to benchmark
  that against a MessagePack baseline. The tagged body was never implemented —
  v1 bodies are project-controlled MessagePack encoded via the `mp_wire`
  runtime — so
  the benchmark instead measures the actually-shipped framing + routing cost
  over a raw `mp_wire` body, as shown above.

## Upgrade and rollback rules

Two kinds of change are distinguished first:

- **Encoding-rule changes** (integer semantics, header layout, the map/array
  structural rules, etc.) — bump `version` and follow the upgrade flow below.
- **Schema evolution** (appended fields/parameters, appended `message_kind`s,
  appended variant tags) — absorbed in-version by the field-number mechanism
  (see [Field-number evolution policy](#field-number-evolution-policy));
  does **not** bump `version` and does **not** require rebuilding deployed
  MPKs: old and new packages keep interoperating through lenient decoding
  (unknown keys skipped, missing fields defaulted). Only guests that want to
  use a new field regenerate their bindings and repackage.

Rules:

- **Upgrade (encoding-rule change):** A future v2 changes the header
  `version`. When v2 is introduced, MPK packages are rebuilt for the matching
  runtime and offline migration handlers convert stored fixtures/test data.
- **No legacy decoders:** the runtime decodes only the current version. A
  message with an unsupported version fails fast with
  `ErrorCode::UnsupportedFormatVersion`.
- **No cross-encoding-version MPK support:** packages are rebuilt per ABI
  version bump; versioning exists to make future encoding-rule upgrades
  explicit and controllable, not to preserve cross-version compatibility.

## Deprecation policy

Version `1` may be deprecated only after:

1. All guest bindings (Rust, C#, AssemblyScript, Python) emit and accept the
   successor encoding version (v2).
2. The new version has been the default for at least one release cycle.
3. MPK packages have been rebuilt against the new runtime.

Deprecation applies to encoding versions; in-version schema evolution
(field-number appends) produces no deprecatable old version.
